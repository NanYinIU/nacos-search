# Own the derived key index's lifecycle outside the cache

The derived `@NacosValue` key index is an application-level service owning its own coroutine scope, and it decides whether it is stale from one number: the version of the cache snapshot it was built from. Before this, the index lived in a stateless object and assembled its own staleness rule out of four facts the cache lent it — a modification counter, a clock accessor, a snapshot of the configurations, and a JVM identity hash standing in for a generation token. Any of those going out of step left gutter markers rendered from a stale index, or rebuilt when nothing had changed, so typing in a Java file could trigger repeated background work for no reason. It also borrowed the cache's scope to run its rebuilds, which meant clearing the cache left derived work running in a scope that no longer made sense.

The cache now hands out a versioned snapshot instead (ADR-0045). Its version advances when the cache's content changes and holds when a mutation is gated away, so the index rebuilds exactly when the underlying data moved. Its as-of instant is the single moment every freshness judgement in one decision is made against, which is what stops a list of matches from straddling a freshness boundary and reporting inconsistent states; a hit cannot be constructed without one, so an unjudged freshness is not a value the code can read. Correctness no longer depends on object identity anywhere.

There is one number, not one per kind of cached thing. Any accepted mutation advances it, including a list-page write or a namespace-index authority mark that the key index does not derive from, so the index can rebuild after a change it did not depend on. That is the deliberate cost of a rule that can be stated in one sentence and cannot be bypassed: a per-kind version would put the derivation back in the business of knowing which parts of the cache it reads, which is the multi-fact staleness rule this decision removes. A rebuild is background work bounded by the cached detail count, and it is coalesced — an ask arriving while one runs is remembered, not dropped, and a rebuild derived from an older snapshot never displaces one derived from a newer.

Visibility is the second rule, and it is not a number on top of the first (issue #126). The composite snapshot version already advances when a block or clear lands, so rebuilds stay version-driven; the extra rule is a serve-time gate: an index records the visibility state it was built under (identity-wide block flag plus the canonical Namespaces hidden by authorization blocks) and is served only to snapshots whose hiding state matches. The previous index for the same identity — served meanwhile on a content-only version move — is therefore never a temporary bypass while a coalesced rebuild runs after a block landed; a metric the derivation must not outlive even for the milliseconds the rebuild takes.

Moving the derivation into the cache was considered and rejected. Extracting keys out of configuration content is configuration-format knowledge, and hosting it in the cache module would make the cache depend on the code-navigation layer — the wrong direction, and a dependency nothing else in the module needs. The index therefore stays in `psi/` and reads the cache only through the snapshot, while the pure derivation and ranking stay separate from the service that owns the cached copy and the scope: the service holds lifecycle, the resolver holds no state and starts no work.
