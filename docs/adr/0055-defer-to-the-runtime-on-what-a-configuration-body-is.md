# Defer to the runtime on what a configuration body is

A gutter marker on `@NacosValue("${a.b}")` is a promise that this placeholder resolves to that line of that configuration when the application runs. It is therefore an assertion about the runtime, and where the plugin's judgement and the runtime's parsing would differ, the runtime wins. Everything below follows from taking that literally rather than as a preference.

The immediate consequence is that the configuration's server-side `type` field takes no part in key extraction, because no runtime reads it. Spring Cloud Alibaba takes the extension from `spring.cloud.nacos.config.file-extension` or from the data id suffix; `nacos-spring-context` takes it from the type declared at the reference site and then from the data id suffix; both default to properties. Nacos 1.4.x blur search does not even select the column. A configuration named `app.properties` and declared TEXT in the console is parsed as properties by the application and yielded nothing by the plugin — the field the plugin trusted was the one field with no authority over the outcome.

So the single accessor that answered both questions is split into two. **声明格式** is what the user picked in the console, and it is a display fact: the result list badge, the detail panel's format tag, and its inline metadata, which previously used two different rules and could print two different names for one configuration. **运行时格式** is what the runtime will read the body as, and it is the only input key extraction takes. The same configuration legitimately displays as TEXT and extracts as properties; a badge and a gutter marker disagreeing is not a defect to reconcile, it is two true answers to two different questions, and the glossary names both so the next change here does not re-conflate them.

The 运行时格式 decision table (issue #171) lives in its own pure unit with its own test, so that changing one row cannot silently change another and so that the table can be verified without a configuration body — the two things a body in the arrangement would quietly undo. It reads the data id suffix: `properties`, `yaml`/`yml`, `json` and `xml` name the format, `txt`/`text`, `html`/`htm` and `toml` name a format no runtime parses, and anything else is undetermined. A type declared at the reference site (`@NacosPropertySource(type = ConfigType.JSON)`) takes a row above these when it lands; it needs a code context, which a data id alone does not carry, so it is an override resolved per reference rather than something the 派生 key 索引 can hold.

The last row is the one place this decision departs from strict runtime fidelity, and the departure is deliberate rather than an oversight. The runtime falls back to properties for an unrecognized suffix, but reading a YAML body under properties rules yields `name` from a line like `  name: svc` — a well-formed key that a real `${name}` placeholder collides with. Following the runtime there manufactures false navigation rather than harmless noise, and since no placeholder the user wrote would have a true hit either way, refusing loses nothing observable and gains an explanation the user can act on. It is the only departure: nothing else in the table is allowed to be more conservative than the runtime, because a refusal the runtime would not make costs the user navigation that would have worked. A suffix the user cased differently is the case in point — `App.YAML` is YAML to Spring Cloud Alibaba, which matches a loader's extensions with `endsWithIgnoreCase`, and to `nacos-spring-context`, which upper-cases the suffix before looking it up — so the table folds case too.

Two things stay outside this. The detail panel's syntax highlighting keeps its own wider vocabulary — it knows sql and html, which will never contribute a key — and stays in the UI layer, because how a body is coloured is not a claim about what the runtime resolves. And the refusal itself is not yet a conclusion the user can see: extraction already returns a closed result carrying its reason, but the callers still flatten a refusal to "no keys", which is how a format the plugin will never parse keeps asking for background Namespace index refreshes. That flattening reaches its own terminal resolution state separately; it is held in one function so the change is one edit.
