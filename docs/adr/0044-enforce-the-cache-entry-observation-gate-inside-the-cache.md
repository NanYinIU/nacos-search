# Enforce the cache-entry observation gate inside the cache module

The cache-entry observation gate moves inside the cache module and takes the observation sequence together with the cache coordinate, so the gate's scope equals the coordinate by construction and no write reaches the store without passing it. Today the gate lives in the operation gateway and is applied by the caller before each write, which leaves configuration history writes and every namespace index write ungated despite ADR-0020 requiring that every cache mutation carry a sequence, and its key truncates the access identity to profile id and access revision, so two identities that resolved to different API generations share one gate and can block each other's writes to distinct coordinates. The two existing implementations are merged rather than one deleted: the gateway's gate raises the high-water when a mutation is accepted, which is what ADR-0020's later-started-accepted rule requires, while the unused session-fencing implementation keys on the complete access identity, which is the correct scope. The visibility-block gate stays outside the cache module and is tracked separately, because it orders dataset confirmation states over access identity, capability and optional namespace rather than cache entries, and because it has no production implementation today; folding it in would make the cache module the owner of the confirmation-state machine as well as of cached data.
