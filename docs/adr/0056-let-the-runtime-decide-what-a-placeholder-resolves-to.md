# Let the runtime decide what a placeholder resolves to

A gutter marker on `@NacosValue("${a.b}")` is an assertion: this placeholder resolves to that line of that configuration when the application runs. The authority for it is the runtime, not our judgement of what looks like a key, and where the plugin's extraction and the runtime's parsing would differ, the runtime wins. What the extractor did instead was decide from the configuration's server-side `type` field, fall back to the data id suffix, default to `text`, and read the body with a hand-written scanner.

That broke in four ways a user could see. Keys were silently lost or invented — a JSON array whose last element is a string destroyed every key defined after it, a YAML sequence of nested mappings collapsed onto index zero, block scalars leaked their body text back as phantom top-level keys, and the bracket form emitted for list elements (`items[0]name.first`) was missing its separator, a shape Spring's relaxed binding can never match. XML contributed nothing, forever, and the empty map it returned was indistinguishable from "parsed, and this key is genuinely absent", so a fully cached XML configuration was classified as *正文尚未加载* — a transitional state allowed to request a background Namespace index refresh, which means a format the plugin would never parse kept asking the server for the life of the IDE. The format judgement trusted the one field no runtime reads. And every failure rendered the same gray hollow icon whose tooltip said the body had not loaded yet, which for XML was a lie whose only available response was to keep waiting.

Neither runtime consults `type`. Spring Cloud Alibaba takes the extension from `spring.cloud.nacos.config.file-extension` or the data id suffix; `nacos-spring-context` takes it from the type declared at the reference site and then the data id suffix; both default to properties, and Nacos 1.4.x blur search does not even select the column. The field the extractor trusted first is the one field with no authority over the outcome.

So the accessor that answered both questions is split, because they are two true answers to two different questions and both are needed at once. **声明格式** is what the user picked in the console — a display fact, shown by the result list badge, the detail panel's format tag and its inline metadata, because misreporting a user's own declaration is its own defect. **运行时格式** is what the runtime will read the body as, decided by the reference-site declaration and then the data id suffix, with 声明格式 nowhere. Displaying as TEXT while extracting as properties is not a contradiction to reconcile. Syntax highlighting is a third consumer with a wider vocabulary of its own — it knows sql and html, which will never contribute a key — and stays in the UI layer.

The supported set follows from that authority rather than from taste: properties, yaml/yml, json and xml are what the two runtimes parse between them, and text, html and toml are what neither parses, so extracting keys for them would manufacture navigation that fails at runtime. TOML reached the Nacos console in 2.3.0, but being offered in a dropdown is not authority.

One row departs from strict runtime fidelity, and it is the only one. A data id with no recognizable suffix is not extracted, though the runtime would fall back to properties: reading a YAML body under properties rules yields `name` from a line like `  name: svc`, a well-formed key a real `${name}` collides with, so following the runtime here manufactures false navigation rather than useless noise, and since no placeholder would have a true hit either way, refusing loses nothing and gains an explanation. Nothing else may be more conservative than the runtime — a refusal it would not make costs navigation that would have worked, which is why a differently cased suffix still resolves. That explanation is a state of its own: **格式不参与解析** is terminal where *正文尚未加载* is transitional, so it never requests a background refresh, and it distinguishes its two reasons because the user's next action differs.

Correctness is measured differentially against the runtime's own property source loaders over a shared corpus, rather than against cases we thought of. That is the authority made executable, and not a stylistic preference: the enumerated unit tests preceding this work were entirely green while JSON silently dropped everything after a string-terminated array. The consequence to hold onto is that a difference between two loaders is a fact to reproduce, not noise to normalize. Spring Boot's YAML flattening terminates on an empty container, so `list: []` contributes the key `list`; Spring Cloud Alibaba's JSON loader drops it, so `{"list":[]}` contributes nothing. Smoothing the two into one rule would feel tidier and would replace a verified runtime fact with our taste — the exact move this decision exists to forbid.
