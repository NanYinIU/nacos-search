# Refresh at the width of the reference, not the width of the Namespace

A code reference that cannot decide from cache — or that decided from a body which has since aged out — refreshes the 配置坐标 it can name and nothing else. `NacosValueLineMarkerProvider` names it in one place: the coordinate of the marker's own top key hit when it has one, so a placeholder resolved by discovery with no `@NacosPropertySource` anywhere still refreshes at coordinate width, and otherwise whatever its reference site declared. `NavigationDetailPrefetchService.requestCoordinate` performs it, bounded to one attempt per coordinate per cache TTL and claimed before the read, which is simultaneously the single-flight for the twenty markers one file puts on the same data id and the failure backoff for an unreachable server — a highlighter pass runs on every keystroke and must never become one request per pass. So one file costs one request per distinct configuration it references, per TTL window, whatever the file's size.

Widening one undecidable placeholder into a whole-Namespace refresh was rejected because the gates that governed it were the same TTL the entries expire under: five minutes after the last load, the first gutter pass over one unresolved placeholder re-read every declared source in the project and paged the entire Namespace, which under the V1 dialect (whose list pages carry bodies, ADR-0048 / issue #146) rewrote every configuration's body — a standing full re-scan every five minutes for as long as one gray icon stayed on screen, to settle a question one detail read answers. The PSI-triggered page walk in `NamespaceIndexRefreshService.requestIfNeeded` is therefore cold-start-only: a Namespace this identity has already indexed still answers "does this data id exist" after its TTL, and only a Namespace with no index at all leaves the question unanswerable. That is the rule the startup preheat has followed since issue #147 (a persisted STALE index counts), now applied to the path that kept paying anyway; re-paging belongs to the gestures that ask for it — manual refresh, Namespace switch, search. A failed load leaves no index behind (the non-authoritative mark only marks an index that already exists), so a genuinely cold Namespace still retries under the coordinator's shared failure backoff. The bounded project-wide body warm sits inside the same gate: it remains its own flight with its own gate (ADR-0043), triggered directly by startup and manual refresh, but on the PSI path a marker that can name a coordinate now refreshes that coordinate itself, so there is nothing project-wide left for it to add on a warm cache. Two consequences are accepted deliberately: absence proofs age out without being rebuilt in the background, so a declared data id that does not exist keeps a hollow icon instead of losing it; and a configuration added on the server enters the Namespace index only on one of those gestures — while a *declared* one is still fetched by coordinate, which is the case a gutter can act on.

Absence is bounded by the freshness of whatever proved it, at every level. `NacosKeyResolver` treats a declared body as authority for its own key set only while that body is inside its TTL; past it, a key the body does not define is 不可判定 rather than 未解析, because the body says nothing about a key added on the server since it was read. Reporting the confident miss from an aged body was rejected because 未解析 paints no icon at all: a key added to an already-declared, already-cached data id was invisible — no icon to click, no state to explain it, and nothing to drive the read that would have resolved it — for as long as the aged body was allowed to speak. The boundary lives in the derived index (`KeyIndex.dataIdsByNamespace` carries each data id's authority instant rather than a bare set) so the index stays timeless and the judgement is made against the snapshot's as-of instant, exactly as `KeyDefinition` does.

Issue #145's refusal to let a resolved-but-aged marker start any work is superseded, and only because the cost changed. What such a marker could ask for then was the namespace-wide sweep, and paying that for a body the user had not even clicked was indefensible; what it asks for now is the one body its icon speaks for. `ConfigReferenceStatus.STALE.mayRequestBackgroundRefresh()` is therefore true, while `RESOLVED` stays false — re-reading a body inside its TTL would make the TTL mean nothing — and the amber icon still renders from cache with nothing waiting on a read, which is the half of #145 that was never about the sweep. Opening a configuration whose cached body is past its TTL confirms that one coordinate too (`DetailController.planSelection`) instead of painting the cached body and stopping: the gutter icon beside it used to turn blue when some unrelated sweep restamped the entry, which read as a refresh that had never happened to the content on screen. Both paths now end in the same place — one read, one coordinate — and differ only in whether the user had to click.
