# Separate navigation detail prefetch from namespace indexing

Namespace indexing fetches configuration summaries only, so preheating a namespace costs one request per summary page instead of one per configuration and its completeness depends on summary pagination alone. Code-reference resolution still needs configuration content to extract the keys a configuration defines, so a separate cancellable and disableable navigation detail prefetch populates the configuration detail cache for that purpose; it is not the implicit per-detail load that ADR-0016 and ADR-0017 forbid on listing and search paths, because it is requested for navigation rather than triggered by a list or a query, and its failure lowers only code-reference decidability, never namespace-index completeness or content-search coverage. The prefetch is bounded by the declared configuration sources — the data ids the project itself declares through configuration-source annotations, the same signal that already hard-filters reference resolution — rather than by an arbitrary item count, so its cost scales with what the code actually references instead of with namespace size; a project that declares none falls back to a request budget and reports the resulting coverage honestly rather than scanning every configuration. Data-id existence checks keep working from summaries alone, so an absent data id still proves an unresolved reference while a missing detail yields an undecidable one; the rejected alternative was to grow the key index lazily from single-detail reads, which keeps ADR-0016 intact but leaves gutter markers silently absent until the user has browsed the configurations that define each key.
