# Own edit and search session state outside the UI

An edit session is created when the user starts editing and is held by a project-level service, not by the detail panel, because ADR-0027 requires a dirty edit to block destroying the tool-window content and closing the project — and a session that lives inside the thing it must block cannot block it. Today no edit session exists during editing at all: it is constructed at the moment the user presses save, from three panel fields, so none of ADR-0027's six blocking rules is implemented and the only consumer of the dirty signal draws a dot on a list row. Publishing, including the final diff and explicit target confirmation ADR-0028 requires and which has no code today, belongs to that same service, since ADR-0027 derives the publish target solely from the session's binding.

Search session context is likewise held by the search service rather than rebuilt per call by the tool window, which currently assembles a request in eight places and fences the results a second time on top of the service's own latest-request-wins ordering. This does **not** contradict the rule that operation modules take an already-captured operation context and never read settings themselves: the service is *given* a context when the project session changes and holds it, which is the opposite of capturing one on demand, and it is precisely what stops a Swing handler from reading the credential store on the event dispatch thread.
