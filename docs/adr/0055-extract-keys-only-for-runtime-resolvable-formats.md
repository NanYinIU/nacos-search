# Extract keys only for runtime-resolvable formats

A gutter marker on `@NacosValue("${a.b}")` is an assertion: this placeholder resolves to that line of that configuration. The key extractor decided which assertions get made, and it decided them from the configuration's server-side `type` field, falling back to the data id suffix and finally to `text`. Anything outside properties, yaml and json returned an empty map, and every caller read that emptiness as "parsed, and the key is not there". A fully cached XML configuration therefore resolved to the undecidable state, whose stated meaning is that the body has not been loaded yet; undecidable is one of the states that may request a background namespace-index refresh, so a format the plugin would never parse kept asking the server for the life of the IDE.

The authority for that assertion is the runtime, not our judgement of what looks like a key. Spring Cloud Alibaba and `nacos-spring-context` between them parse properties, yaml/yml, json and xml, and neither has ever had a parser for text, html or toml — toml reached the Nacos console in 2.3.0, but no runtime reads it. Neither runtime consults the server-side `type` field at all: Spring Cloud Alibaba takes the extension from `spring.cloud.nacos.config.file-extension` or the data id suffix and defaults to properties, and `nacos-spring-context` takes it from `@NacosPropertySource(type = …)`, falling back to the data id suffix and again to properties. Older Nacos servers do not even return `type` on a blur search. The one field the extractor trusted first is the one field no runtime reads.

The **declared format** and the **runtime format** are therefore separate facts about the same configuration, and both are needed at once. The declared format is what the user picked in the console; it is what the result list badge and the detail panel's format tag must show, because misreporting a user's own declaration is its own defect. The runtime format is what the runtime will read the body as: the type declared at the code reference site first, then the data id suffix, and the declared format nowhere. A configuration named `foo.properties` and declared `text` displays as TEXT and is extracted as properties, and that is not a contradiction — it is two true answers to two different questions. Syntax highlighting is a third consumer with a wider vocabulary of its own (it knows sql and html, which will never contribute a key) and stays in the UI layer.

A data id with no recognizable suffix and no declared type at the reference site is **not** extracted, even though the runtime would fall back to properties. This is deliberate and it is the one place this decision departs from strict runtime fidelity. Reading a yaml body with properties rules yields `name` from a line like `  name: svc` — a perfectly well-formed key that a real `${name}` placeholder will collide with, so following the runtime here manufactures false navigation rather than merely useless noise. The observable outcome is the same either way (no placeholder the user wrote will have a true hit), so refusing to extract loses nothing and gains an explanation.

That explanation is a state of its own. **格式不参与解析** is terminal where the undecidable state is transitional: it never requests a background refresh, it carries its own gutter icon — the same stroke geometry as the other three with the jump arrow removed, because there is nowhere to jump — and it says which of two things happened, since the user's next action differs. A `.txt`, `.html` or `.toml` suffix has no next action. A data id with no recognizable suffix declared as json has one: rename it or declare the type in code. Attribution requires a data id context; without one a miss cannot be blamed on any particular configuration and the existing states still apply.

Two consequences shape the implementation. A type declared at the reference site cannot enter the derived key index, because the index is built once per snapshot over every cached configuration and has no code context — the same configuration could need extracting two ways for two reference sites. The index is therefore built from what a configuration can decide about itself, and a code-site declaration is an override resolved per reference against that one data id, which is already a hard constraint there. And correctness now rests on parsers rather than on our own scanner: snakeyaml for yaml (the library Spring Boot itself uses, so the two cannot disagree about yaml, and its marks give line numbers for free), the already-bundled gson `JsonReader` for json, and `java.util.Properties` for properties. Where a parser gives no line number the key set and the line number are derived separately — a wrong line misplaces an icon, a wrong key set invents or loses navigation, and the two must not share a failure. The oracle for "correct" is the runtime itself, asserted by differential test, because the enumerated unit tests that preceded this were all green while json silently dropped everything after an array whose last element was a string.
