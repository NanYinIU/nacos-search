# Make search targets unnameable outside the search service

The search request type and the request-taking search entry point carry an opt-in requirement, so naming either one from a Swing panel is a compile error rather than something review has to notice. ADR-0046 gives the search service the session context to hold; this closes the other half, which is who may name a search's target at all. It is the same instrument ADR-0052 applies to cache writes, for the same reason: "the tool window expresses intent and never names an environment" is an architecture-fitness property rather than a behaviour, and a test would pin the current call sites instead of the property.

The failure it prevents is documented rather than hypothetical. The tool window assembled a search request in eight places — namespace change, search, type-ahead, previous page, next page, page size, refresh, and the list load — each deciding again which profile, namespace, and operation context the search targeted, and seven of them from an event-dispatch-thread handler. They did not agree: some passed a prepared context, some passed none, one re-derived the profile after the selection had already moved. A convention that every new handler must consult the same three things is exactly the kind this codebase has not been able to keep.

The layering is not arbitrary. A search's target is the session the service was given when the project session changed, and only the service holds it; a Swing handler that wants to name one has nothing correct to pass. It can read the credential store on the event dispatch thread, which ADR-0039 forbids, or it can reuse a prepared snapshot that may already name the environment the user left. Both were live here. The intents the window is left with — search this, next page, this page size — carry no target and need none, and reads of what the service publishes carry no such requirement at all.

A Kotlin opt-in marker was chosen over the alternatives available in a single Gradle module, on the same grounds as ADR-0052: Kotlin has no package-private visibility, `internal` is module-wide and therefore no boundary here, and a Gradle subproject per layer would restructure the build for a slice with no runtime logic. Opting in belongs to the search service, which holds the session, and to the tests that assert what a request derives from its criteria.

One consequence is worth stating, because it looks like a gap. The window is left with a controller that mostly delegates. That is the point: what the controller does not delegate is the session handoff — capturing the operation context off the event dispatch thread and handing it to the service in an order that a slow capture cannot invert — and holding it outside Swing is what makes the window's orchestration testable at all. The window had no test file before this.
