# Resolve the API generation on cache hot paths

The code-navigation, UI, and local-search paths derive their access identity without reading a credential, because reading `PasswordSafe` on the EDT is forbidden (ADR-0039). The resolved API generation is part of that identity by design — a V1 and a V3 read of the same configuration are different observations and must not share an entry (ADR-0034) — but for a profile whose API policy is AUTO the generation is not in the profile. It is resolved per operation. Those paths used to map AUTO straight to an unknown generation, so under the default policy the plugin read one key space and wrote another: local search over the cache came back empty, the startup key-index warm counted nothing, the detail panel's freshness line reported an entry that was cached as absent, its authoritative not-found deleted a coordinate nothing had written, and clearing a namespace invalidated a space nothing lived in.

The generation is now looked up, not assumed, from the two credential-free sources that already hold it: the generation this project session resolved, valid only while the profile id, profile revision, and access revision it was resolved under still hold; and failing that the last-known generation persisted by profile id, access revision, and canonical endpoint, whose stated purpose in ADR-0034 is to locate the same identity's unconfirmed cache in a later session. A project's own hot path asks that project's session directly, because sessions are per-project (ADR-0004). Application-level readers have no project of their own and ask the session of whichever open project selected the profile — the same lookup the operation layer uses to decide where to commit a resolution. When no open project owns the profile, the operation layer commits to a session of its own that nothing else can reach; the persisted value is what carries the answer across that gap, which is the second reason it is not merely an offline-restart convenience.

Convergence is achieved by giving the hot path the resolved value, never by dropping the generation from the key or letting a lookup override one. An identity that already names V1 or V3 is returned untouched, so a locked profile behaves exactly as before, and two identities differing only in resolved generation stay mutually invisible. Locating a generation authorises nothing and confirms nothing: formal detection still runs before any remote operation, an entry found this way is still unconfirmed and what may be *shown* from it after a failed detection is still ADR-0034's failure matrix, a newly resolved different generation still switches identity and advances the session epoch, and hiding cached data when access is refused remains the visibility gate's job.

When neither source has a value the identity keeps its unknown generation and the read is a miss. That is the outcome ADR-0034 requires — without a matching last-known value AUTO exposes no cache — and it is why the gutter marker's compensating write is now deleted rather than kept. That write existed only because the marker read a space nothing else wrote to, so it filled the space itself; what it filled was configuration data no successful formal detection had confirmed. With one key space per environment it would be a plain duplicate of the gateway's write, and the code-navigation layer is not entitled to make one (ADR-0052).
